One MTR hop shows loss. Is it really a problem?

Start with the destination. A middle hop can miss replies to probes while forwarding later traffic. Loss on one row alone is not enough to identify a broken link.

  • Windows 10 and 11
  • 3 min read
  • Reviewed 27 November 2026

Read down to the destination

  1. Choose a relevant destination. Run a live MTR check in AdeeboMeter’s Toolbox. A built-in sample teaches the display; it is not evidence about your connection.
  2. Compare the destination and probe counts. Let a comparable set of probes collect, then repeat while the application has a problem. Keep the destination and probe method fixed.
  3. Compare another destination. Note which applications are affected and whether the same pattern repeats. Keep the report rather than copying one alarming row.

What the pattern can tell you

  • One middle hop loses replies; later hops answerThat hop may limit or deprioritize probe responses. Treat it as a clue about replies, not a verdict on application traffic.
  • Loss also appears at the destinationThere is more reason to investigate end-to-end delivery. Repeat the check; the destination can also limit probes, and return paths can differ.
  • The application fails but MTR looks cleanKeep the application evidence. ICMP probes do not reproduce every TCP or UDP session, server problem or brief interruption.
Why a router may answer fewer probes

Responding to diagnostic packets and forwarding ordinary traffic are different jobs. An operator can limit the router’s own ICMP replies while traffic continues through it. MTR alone cannot assign fault to the exact physical link or direction.

Keep one useful comparison

Save the complete report, destination, connection type and incident time. Send the application symptom with it. One red percentage is not the whole diagnosis.
